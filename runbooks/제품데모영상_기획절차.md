# 런북 — 제품 데모 영상(SaaS/앱/AI 서비스) 기획

> 요약: 제품 정보를 받아 40초 UI 모션그래픽 데모의 콘셉트·대본·장면 명세·구현 spec 까지 만드는 절차. "우리 제품 홍보영상 만들어줘" 요청이 오면 연다. 일반 정보 전달 영상은 runbooks/정보전달영상_제작절차.md.

## 역할
30~45초 안에 기능 하나를 이해시키는 **제품 데모 기획자이자 모션 디렉터**로 일한다.
단순 화면 녹화가 아니라 브라우저 목업·커서·클릭 피드백·확대·UI 상태 변화를 조합한 UI 모션그래픽을 만든다.

## 1. 영상 하나에 담는 것 (넷만)
- 고객 문제 **하나**
- 핵심 기능 **하나**
- 구체적 결과 **하나**
- 행동 유도 **하나**

여러 기능을 억지로 넣지 않는다. 기술 설명이 아니라 **사용자가 얻는 변화**를 보여준다.

## 2. 7단 구조 (엔진이 강제한다)
| # | role | 목적 |
|---|---|---|
| 1 | `hook` | 시청자가 겪는 문제를 질문으로 제시 (첫 3초) |
| 2 | `problem` | 기존 작업의 불편함을 짧게 묘사 |
| 3 | `solution` | 제품과 핵심 기능 소개 |
| 4 | `demo` | 요청부터 결과까지 실제 사용 흐름 |
| 5 | `differentiation` | 기존 방식과 다른 점 |
| 6 | `result` | 시간 절약·완성된 결과 |
| 7 | `cta` | 다음 행동 하나 |

**기본은 30초다.** `"profile": "product-demo-30"` → 7장면·각 2~6초·총 30초·CTA 2초 이상·role 순서를 게이트가 검사한다.
40초(`product-demo-40`)는 담을 내용이 확실히 많을 때만 쓴다 — 같은 내용을 40초에 담으면 장면당 5~7초가 되어 늘어진다.
시작 파일: `engine/specs/template-product-demo-40.json`, 실제 사례: `engine/specs/carfia-30.json`

## 3. 문장 원칙
- 쉬운 한국어. 한 문장 20자 내외, 화면 문구는 한 장면에 **최대 두 줄**(`statement` 스키마가 3줄을 거부)
- 첫 3초 안에 문제 또는 강한 이점
- "혁신적인", "획기적인", "올인원" 같은 모호한 표현 금지
- 기능이 아니라 **사용자의 행동과 결과** 중심
- 확인되지 않은 수치·성과·고객 반응을 만들어내지 않는다
- 내레이션과 화면 문구를 똑같이 반복하지 않는다. **내레이션 없이도 이해되게** 구성한다
- 사용자가 제공하지 않은 기능을 발명하지 않는다 ← 가장 자주 어기는 규칙

## 4. 기본 설정 (지정이 없으면)
**30초** / 9:16 / 1080×1920 / 30fps / 장면 7개 / 장면당 2~6초 / CTA 최소 2초.
**자막은 1.2~1.6초마다 바꾼다.** 2초를 넘기면 "느리다"는 말이 나온다(실측: 카피아 1차본 2.3초 → 느림 지적).
대상: Threads·Reels·Shorts. 배경은 밝은 아이보리(`pastel` 팔레트) 또는 브랜드 컬러.

## 5. 모션 원칙
- **첫 3초에 움직임이 있어야 한다.** 글자만 페이드되는 훅은 넘겨진다.
  막대가 차오르거나, 커서가 움직이거나, 요소가 쌓이는 장면으로 연다 (카피아 1차본의 실패 원인)
- **사람을 안 쓰면 화면을 꽉 채운다.** `talkingHead: null` 이면 엔진이 알아서 그래픽을 키우고 자막을 내린다.
  (`full-graphic` 아래쪽 빈 공간은 원래 토킹헤드 자리다)
- 중요한 화면을 한 번에 **하나만** 보여준다
- 커서는 실제 사용 순서대로 움직이고, 클릭 순간 원형 글로우를 준다 (`browser-mock` 의 `cursor[].click`)
- 핵심 화면은 105~115% 느린 확대 (`zoom`, 스키마가 1.15 초과를 거부)
- 등장은 ease-out, 텍스트는 페이드 + 짧은 이동
- 자동화 기능은 **입력 → 처리 → 결과**의 상태 변화로 표현
- 실제로 없는 클릭·기능 실행 장면을 만들지 않는다
- 과도한 줌·회전·글리치·파티클 금지

## 6. 정보가 부족할 때 (최대 5개만 묻는다)
제품명 / 누구를 위한 제품인지 / 이번에 보여줄 핵심 기능 하나 / 사용 전 불편함과 사용 후 결과 / 마지막에 유도할 행동.
일부가 없어도 합리적으로 가정할 수 있으면 묻지 말고 진행하고, **가정한 내용을 결과 맨 위에 표시**한다.

## 7. 산출물 형식
1. 기획 요약(제품·타깃·문제·핵심 기능·기대 결과·핵심 메시지·CTA·길이/비율·적용한 가정)
2. 최종 내레이션 (연출 설명 섞지 않고 그대로 읽을 수 있게)
3. 장면별 제작 명세 표: 장면 / 시간 / 목적 / 화면 구성 / 화면 문구 / 내레이션 / UI·커서 / 모션·전환 / 사운드
4. 필요한 에셋 체크리스트 (형식·크기 포함)
5. 모션 디자인 명세 (값으로: 시간·크기·거리·투명도·배율)
6. **spec JSON** — 이 레포에서는 "Remotion 구현 프롬프트" 대신 `engine/specs/*.json` 을 직접 쓴다
7. 자체 검수 (아래)

요청 템플릿과 작성 예시: `factsheets/제품데모_요청템플릿과예시_20260914.md`

## 8. 자체 검수 (통과/수정 필요로 판정, 수정 후 최종본만 제시)
- 첫 3초 안에 문제나 이점이 제시되는가
- 기능 하나에 집중했는가
- 화면만 봐도 이해되는가
- 내레이션과 화면 문구가 불필요하게 겹치지 않는가
- 제공되지 않은 기능을 발명하지 않았는가
- 장면 시간 합계가 정확한가 → `npm run lint:spec` 이 대신 판정
- CTA 가 하나로 명확한가
- 작은 화면에서도 문구가 읽히는가 → 글자 크기 자동 축소 + 게이트가 판정

## 9. 실행
```bash
cd engine
cp specs/template-product-demo-40.json specs/<제품명>-40.json   # 복사해서 시작
# src/specs.ts 에 import 한 줄 추가
npm run lint:spec          # 7단 구조·시간·문구 길이 검사
npm run studio             # 미리보기
npx remotion render <id> out/<제품명>.mp4
```
